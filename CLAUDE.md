# HomeSage

HomeSage is a retrieval augmented assistant over a real estate MySQL database, reached by chat or by phone. A user asks about properties in plain English, the API works out whether the question needs SQL filters, semantic search or both, pulls rows, and an LLM writes an answer that cites the property IDs it used. Answers stream to an Angular UI with property cards, and a voice agent answers callers through the same API.

## Ground rules

1. MySQL is the source of truth. Elasticsearch is a derived index that can be rebuilt at any time.
2. The LLM never answers from memory. Every fact in an answer must trace back to a retrieved row and carry a citation like `[P-1234]`.
3. The API connects to MySQL with a read only user. Never use root, never write to the property tables.
4. Generated SQL always goes through the validator before it runs. No exceptions, including in scripts and tests.
5. No LangChain or similar frameworks in core paths. Call provider SDKs directly.
6. Scope is fixed per issue. New ideas go to `docs/backlog.md`, not into the current branch.
7. Every listing in this repo is made up, generated by `npm run db:seed`. **Never commit real addresses, phone numbers, names or seller text**, including in tests, docs and eval reports. Read `docs/data.md` before touching the schema, seed, document builder or prompts.

## Stack

* Three independent apps, `api/`, `web/` and `voice/`, each with its own `package.json`, lockfile and `node_modules`. npm, Node 24, TypeScript strict
* `api`: NestJS 12, native ES modules. Owns every request and response contract in `api/src/contracts/`
* `web`: Angular 21, standalone components, Signals, zoneless, Tailwind. Imports contracts from the API through the `@api/contracts` alias
* MySQL 8, Elasticsearch 8 (`dense_vector` plus BM25), Redis
* Pino for logs
* Vapi for the phone line in `voice`, with SQLite for its bookings and call log
* Vitest, Supertest, Testcontainers; one shared ESLint and Prettier config for all three apps
* GitHub Actions for CI

## Commands

Each app is installed and run from its own folder. Install `api` before building `web`, because the web app compiles the API contracts. Some scripts will not exist until the milestone that adds them.

```
cp .env.example .env                      # once, then set MYSQL_ROOT_PASSWORD
docker compose up -d --wait               # mysql, elasticsearch, redis, ollama

cd api
npm install
npm run start:dev                         # API on port 3000
npm run lint
npm test                                  # unit tests
npm run test:e2e
npm run db:seed                           # generate the made up listings into MySQL
npm run ingest -- --full                  # rebuild the ES index from MySQL
npm run ingest -- --since <ts>            # incremental sync
npm run evals                             # full eval run, writes to workbench/evals/reports

cd web
npm install
npm start                                 # web app on port 4200
npm test

cd voice
npm install
npm run start:dev                         # voice agent on port 3100
npm test
npm run test:e2e
```

## Layout

```
api/src/
  contracts/   Zod schemas and types for every request and response; the only API folder the web app may import
  app/         features: chat, router, sql, retrieval, embeddings, ingestion, llm, health
  platform/    our own cross cutting machinery: request-context, logging, tracing, throttler, filters, cache
  infra/       adapters and boot config: config, mysql, elasticsearch, redis
  core/        internal interfaces only (LlmProvider, EmbeddingProvider, HealthIndicator)
api/tools/     command line tools (the seed and the eval runners), outside the server build
web/src/app/
  <feature>/   chat, property, layout
  resources/   the only code that calls the API
  config/      static data and pure selectors
  ui/          shared presentational components
workbench/     everything that supports the apps without being one
  docker/      container init scripts (the read only MySQL user)
  guards/      the CI check that no real looking postcode or phone number enters the repo
  evals/       golden set, hostile inputs, committed reports (the runner is api/tools/evals)
voice/         the phone agent: src, Vapi sync tool and system prompt
docs/          ADRs, data, schema, chat stream, UI components, backlog
```

Backend dependencies point one way: `app` to `platform` to `infra` to `core`. There is no `utils` or `common` folder anywhere.

## Rules, skills and notes

* `.claude/rules/` holds coding rules scoped by path, so the backend, frontend and shared rules apply to the files they cover. Start with `shared/code-style.md` and `shared/workflow.md`.
* `.claude/skills/` holds repeatable procedures: `plan-issue` before starting non trivial work, `review` for pull requests, `cleancode` as a pre commit checklist, `fishy` for tracing suspicious code, `self-improve` after a task goes badly.
* `.claude/context/architecture.md` covers the request flow and design decisions.
* `.claude/context/milestones.md` says what is built and what is not.

## Working habits

* Keep changes small and tied to one issue.
* Write or update tests in the same change as the code.
* Run anything that touches a real service against the local Docker stack before calling it done.
* If a schema, prompt or config shape changes, update the matching doc in `docs/` too.
* When a decision has real tradeoffs, write it up as an ADR in `docs/adr/`.
* Do not add dependencies without a clear reason stated in the PR.
